# 定时脚本普通子进程启动（0.1.13）

## 依据与本次范围

用户已在 Cloudaemon 中验证：0.1.12 原生插件采用普通子进程启动后 SVN 工作副本识别恢复，移走旧克隆目录后可以执行同步。定时器的脚本分支仍采用挂起启动、自建 Job Object、恢复线程，因此本次将 Windows 的「脚本」动作改为相同普通启动策略。这是基于插件现场结果的兼容性修复，尚未证明 git-bash 定时任务实机已恢复。

- 脚本任务：保留 CREATE_NO_WINDOW，去掉挂起启动和自建 Job；不 breakaway、不提升权限、不修改沙箱策略。
- 只执行用户配置的解释器，不寻找或替换为同目录的 bash/sh，不添加登录 Shell 参数，不修改 PATH/HOME/MSYSTEM；保留任务显式环境覆盖。
- 沿用逻辑盘路径传参及配置工作目录，不解析为物理工作盘路径。原定时定义无需迁移。
- 取消或超时在解释器仍运行时通过系统目录的 taskkill /PID /T /F 尽力停止进程树，最多等待 2 秒；失败请求停止直接子进程并报告树停止未确认。
- 直接 exe 动作保留原自建 Job 管理；应用启动及原生插件分支保持各自规则。

## git-bash 启动器的限制

[Git for Windows 官方说明](https://gitforwindows.org/git-wrapper.html)指出 git-bash.exe 属于设置环境并启动实际程序的包装器。因此严格使用 git-bash.exe 时，宿主记录的是直接启动器进程的退出结果；终端内脚本可能有自己的生命周期，标准输出也可能不回传小工坊。执行记录明确提示应核对脚本日志或产物，不能将退出码 0 单独作为脚本业务完成证据。

普通启动不提供自建 Job 的宿主崩溃自动清理保证，也不能保证已脱离父进程的终端或辅助进程被取消。尚在其他终端运行的脚本不得与新计划并行重复执行。

## 验证

调度器本机 14 项、前端 23 项通过，前端构建通过；Windows 调度器测试代码交叉检查及整机在线安装包构建通过。Windows 专用回归覆盖所选 git-bash.exe 不被替换、中文与空格工作目录/参数、脚本产物和 MINGW 环境、bash 超时；这些测试本次仅编译，尚未在 Windows 执行。现有直接 exe Job 测试保留。上下文诊断脚本本机冒烟测试通过。

## 用户验证顺序

1. 安装 0.1.13，复制原定时任务并保持暂停，保留所选 git-bash.exe、工作目录、环境配置。
2. 将目标暂改为同包 `check-context.sh`，放在沙箱内可写目录。有序参数填一个已知仅沙箱内可见文件的逻辑路径，只检查是否存在和可读。
3. 手动执行复制任务，在脚本目录查看新生成的 handykit-context-*.log；核对 MSYSTEM、bash/sh/git 工具位置和目标文件可见性。
4. 确认诊断正确后再用原业务脚本手动验证。业务脚本可能 push/commit，应避免与原插件或定时计划重叠。
5. 业务产物和远端状态确认正确后，再启用需要的唯一同步计划。若未生成诊断报告，提供定时执行记录的消息、退出码与错误输出。
